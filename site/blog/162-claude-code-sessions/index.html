What 162 Claude Code sessions taught me about silent failures

The strongest signal was not widespread cheating. It was how easily trace-based verification can look at the wrong part of the work.

I built Assaystone around a deliberately uncomfortable question: when an agent says the work is done, what independent evidence proves it? The pitch can sound like “catch agents deleting tests.” Before trusting that framing, I ran the audit over my own local Claude Code history.

The corpus was 167 JSONL transcript files, about 578 MB, reduced to 162 usable sessions. Everything ran offline. I reconstructed file edits from Write, Edit, and MultiEdit tool calls, then applied Assaystone's default path, syntax, diff, debug-print, and evidence rules. This was one user's corpus with no human labels. The numbers are signals, not confirmed defects.

The result changed how I describe the product.

1. Test edits are common. Test tampering was not.

Twenty-eight sessions, 17% of the corpus, touched test files. That sounds alarming until you look at the denominator: 27 of those sessions also touched source files. Normal feature work usually changes implementation and tests together.

Only one session edited tests without editing source. It looked like the strongest possible signal. Manual review found a test fixture and schema refactor during an upstream bug investigation. The task had explicitly asked for that work.

A path-based rule can tell you that test files changed. It cannot tell you whether the agent protected the product or protected itself.

I manually triaged the five strongest candidates overall, including four sessions that wrote into test-like paths through shell commands. None were confirmed test tampering. One added new tests. Three wrote temporary probe scripts or delivery notes whose contents happened to mention test paths.

The honest product claim is therefore not “Assaystone detects cheating.” It is: Assaystone makes the acceptance boundary explicit, testable, and reviewable. Path-based test integrity is a useful warning, not an intent detector.

2. The audit's biggest blind spot was Bash.

Bash was 20,688 of 28,082 tool steps, roughly 74%. That is not an implementation detail. If a verifier only understands editor tool calls, it misses most of what the agent actually does.

Sixty-one sessions wrote files through shell commands such as cat >, tee, sed -i, patch, perl -pi, and git apply. Sixteen of those had no Edit or Write artifacts at all. Four wrote into paths that looked like tests.

That led to a concrete change for Claude Code: the Stop hook merges git working-tree changes when it runs inside a repository, so Bash-made edits become visible to path, syntax, and diff checks. Transcript replay still has limits, but the acceptance layer no longer pretends that the editor is the whole interface.

3. A 200-step budget treated long work as failure.

Forty-six sessions exceeded 200 steps. The median was 96, p90 was 347, and the longest reached 2,440. A low budget catches runaway loops, but it also marks ordinary long debugging sessions as suspicious.

The default moved to 5,000. That is not an acceptance threshold. It is a guard against something that failed to stop.

4. “All tests pass” is usually not the final sentence.

I expected final messages to be full of unsupported success claims. A strict claim check found zero sessions. Real agent endings were mostly summaries, not acceptance statements.

That matters for verifier design. The useful evidence is often the exit code from the test command, the files that changed, or the relationship between an action and its result. Parsing impressive-sounding prose is a weaker foundation than checking structured evidence.

What this means for agent verification

The first version of a verifier is usually a proxy. A path rule proxies for “the agent weakened tests.” A step budget proxies for “the agent is stuck.” A final-message check proxies for “the agent lied.” Each proxy is useful only when its distance from the real property is visible.

Assaystone's contract model treats determinism and uncertainty as first-class:

  • Pass when independent evidence supports the requested property.
  • Fail when the property is contradicted by concrete evidence.
  • Escalate when the available checks cannot decide safely.

This is also why mutation testing and backtesting matter. A verifier that always fails is not safe; it is noise. A verifier that never fails is not independent; it is decoration. Inject labeled defects, measure recall, measure false alarms, and compare the result to human labels.

Reproduce the aggregate audit

The corpus script is read-only. It does not modify transcripts or repositories and makes no model calls.

pip install assaystone
git clone https://github.com/yellowsand1/assaystone
cd assaystone
python scripts/corpus_audit.py --root ~/.claude/projects

If your corpus produces very different numbers—especially the Bash-only write rate or the share of sessions over 200 steps—that is exactly the kind of evidence the project needs. The Failure Zoo is open for redacted traces and minimal reproductions.

Limits

This was a single-user corpus with no human labels. Transcript replay only sees structured tool calls; shell coverage depends on git state. The strongest candidates were manually reviewed, but the broader corpus was not labeled by a second reviewer. Treat the findings as a calibration exercise, not a prevalence study.
